# Intent Spec — 面向 Intention Group Review 的需求引导与拆解

## 核心目标

下游 Code Review（尤其是 AI Diff Review）最大的痛点是：改动按文件路径混成一锅粥，核心逻辑、顺手重构、共享类型修改缠绕在同一个 Diff 里，导致审查者难以判断「为什么要改」以及是否夹带了范围蔓延（Scope Creep）。

本 Skill 的作用是在**动手写代码或正式立项之前**，用极低的心智负担把用户的原始想法收敛成一份**正交的意图分组对齐卡（Intent Alignment Card）**：
1. 让最终产出的代码变更天然落入几个边界清晰的 **Intention Groups（意图组）**。
2. 按改动规模自适应裁剪（L1 / L2 / L3），**严禁把微小的改动逼成八股文填表**。
3. **人说大白话 → AI 结合代码上下文起草精简对齐卡 → 人花 15 秒确认 → 按需落盘或按意图组原子化实现**。

---

## 工作流

### 第 1 步：静默轻量探查上下文（若在代码仓库内）

不要让用户替你查代码，也**不要在对齐阶段修改任何业务代码**。起草对齐卡前，快速做有界探查：
- 检查项目是否有 `AGENTS.md`、`CLAUDE.md` 或已有的 Spec 目录规范（如 `docs/specs/`、`specs/`）。
- 定位需求涉及的 2～5 个关键文件、数据模型、公共工具或上下游调用方，确保后续填写的 `Impact`（影响面）和意图拆解基于真实代码结构，而非凭空臆测。

### 第 2 步：判定复杂度等级（L1 / L2 / L3），拒绝形式主义

根据改动波及范围自动定级，只输出匹配当前体量的要素：

| 等级 | 典型特征 | 对齐卡体量与必填项 |
| :--- | :--- | :--- |
| **L1：单意图微改** | 1～2 个文件、单一明确行为调整、无跨模块副作用 | **3～6 行极简卡**：`Why`（一句话动机）+ 单一 `Intention`（改什么 & 验收不变量）。免填长篇 `Impact` / `Non-Goals`（除非存在隐蔽兼容风险）。 |
| **L2：常规特性（默认）** | 跨 3～12 个文件，涉及契约/逻辑/UI/测试等多个环节 | **15～25 行标准对齐卡**：`Why` + 2～4 个正交 `Intention Groups` + 关键 `Impact` + 针对性 `Non-Goals`。 |
| **L3：高风险 / 架构重构** | 核心状态机重写、DB 迁移、公共 API 破坏性变更 | **完整 Spec 卡**：除标准四要素外，显式列出分组间的**先后依赖/回滚边界**、存量数据兼容策略及待拍板的技术取舍。 |

各等级的具体好坏对比示例见 [references/examples.md](references/examples.md)。

### 第 3 步：按「可独立 Review 的 Intention Group」拆解 `What`

拆解子意图时遵循以下 5 条工程准则——每一条子意图都应直接对应未来 PR / Diff Review 面板里的一个独立分组标题：

1. **按语义目的（Why）分桶，绝不按文件名记流水账**
   - 错误：`1. 改 order.ts  2. 改 schema.sql  3. 改 OrderCard.tsx`
   - 正确：`1. [数据契约] 扩展订单超时字段与类型定义  2. [核心逻辑] 实现超时拦截与自动取消  3. [视图接入] 订单卡片展示倒计时态`
2. **前置纯重构必须与业务行为变更物理隔离**
   - 如果旧代码太乱需要先整理，必须单独拆出 `Group 1: [前置重构] ...`，并写明验收不变量：`纯结构提取，现有业务行为与存量测试 100% 不变`。绝不允许在同一个代码块里边重构边改业务逻辑。
3. **共享模块与公共契约变更必须显式高亮**
   - 触碰全局 `utils`、跨模块共享类型、中间件或 Schema 时，要么独立成组，要么在 `Impact` 中点名受影响的下游调用方，提醒 Review 时重点精读。
4. **每个意图组附带一句「可验证的不变量（Invariant）」**
   - 不要写“功能正常”、“代码整洁”这类废话；要写 Review 时能直接拿来对账的硬约束（例如：`存量无该字段的历史记录默认按“永不超时”处理，不抛异常`）。
5. **用 `Non-Goals` 封死 Scope Creep 与噪音**
   - 包含两部分：**本次不碰的相邻业务边界**（如 `仅处理创建订单链路，不改售后退款链路`）+ **防噪铁律**（禁止顺手重命名无关变量、禁止混入纯格式化变更）。

### 第 4 步：少盘问、先给草稿卡，只追问关键分叉

不要像审讯一样先抛五六个空泛问题让用户回答。人修改一份具体草稿的成本远低于从零填空：
- **存在颠覆性分叉时**（例如两种方案会导致完全不同的架构或意图拆解）：最多提 **1～3 个简短选择题**（可用交互提问工具或列表），给出你的推荐项。
- **其余常规情况**：基于合理假设**直接在对话中输出对齐卡草稿**，将不确定的 1～2 个假设浓缩在卡片底部的 `待确认点` 中，请用户一句话拍板或微调。

## 对话内「精简对齐卡」输出模板（L2/L3 通用骨架）

在对话中首次呈现或迭代时，保持紧凑易扫读：

```markdown
## 📋 需求对齐卡：<简短需求标题> `[L2 常规特性]`

### 1. Why（背景与核心动机）
- <1~2 句话说明解决什么业务痛点或修复什么根因，不写实现细节>

### 2. Intention Groups（按意图拆解的变更组）
1. **[意图组 1：<动词 + 对象，如「前置重构：提取结算时间纯函数」>]**
   - **改动内容**：<涉及的模块职责与核心动作>
   - **验收约束（Invariant）**：<可直接核对的确定性结果/兼容要求>
2. **[意图组 2：<如「数据与契约：新增超时字段」>]**
   - **改动内容**：...
   - **验收约束（Invariant）**：...
3. **[意图组 3：<如「核心逻辑与单测：超时拦截与自动取消」>]**
   - **改动内容**：...
   - **验收约束（Invariant）**：...

### 3. Impact（影响面与重点审查区）
- **波及模块 / 公共代码**：<点名修改的共享类型、公共函数、接口契约或迁移脚本；无则写「局限于 X 模块内部」>
- **兼容性 / 存量数据**：<老客户端、历史数据、开关降级策略>

### 4. Non-Goals（明确不做与防噪边界）
- <业务边界：本次明确不处理的相邻场景>
- **工程防噪**：严禁顺手重命名无关符号或格式化无关代码；纯重构与新逻辑分拆独立分组/Commit。
```

> 紧接卡片下方用一两句话向用户确认：
> - 意图拆解与边界是否准确？
> - 确认后需要 **保存为 Spec 文档**（默认 `docs/specs/YYYY-MM-DD-<slug>.md` 或项目既有目录）、**直接按意图组开始实现**，还是**复制为 Issue / PR 描述**？

## 第 5 步：确认后的消费与交付衔接

用户确认对齐卡后，按其选择的消费路径执行：

### 路径 A：落盘为 Markdown Spec 文件
1. 优先遵循仓库已有的 Spec 目录命名（如 `docs/specs/`、`specs/`、`rfcs/`）；若无现成目录，默认写入 `docs/specs/YYYY-MM-DD-<slug>.md`。
2. 在落盘文档末尾附带一段简短的 **《交付与审查约定（Execution & Review Contract）》**，供后续接手的 Coding Agent 或开发者遵循：
   - 严格按上述 `Intention Groups` 顺序推进，每完成一组验证对应 `Invariant`，理想情况下每组对应一个语义清晰的原子 Commit。
   - 若编码过程中发现必须突破 `Non-Goals` 或新增公共模块改动，需先更新 Spec 或单独拆出新的 Intention Group，禁止静默混入现有分组。

### 路径 B：直接进入按意图分组开发
1. 严格以确认后的 `Intention Groups` 作为执行清单，**一组一组推进**，保持 Diff 边界干净（不在修核心逻辑的 Hunk 里夹带无关整理）。
2. 如果项目使用 Git 且任务允许提交，可按每个 Intention Group 拆分为独立原子 Commit；若保留在工作区供用户本地 Review，则在最终汇报时**严格按 Intention Group 列表逐组说明改动文件、对应行号与验收结果**，并主动声明是否存在任何计划外的附带修改（Intent Drift = 0）。
